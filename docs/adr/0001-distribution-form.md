# ADR 0001 · 先做网站，DSH 插件作为后置分发渠道

- 状态：已接受（2026-11-19）
- 决策者：项目所有者
- 关联：[设计文档](../设计文档.md)、[需求分析](../docs/需求分析.md)

## 背景

产品是「harness 插件的 Star 竞速榜 + 发现 + 变现」。核心价值来自**所有用户共享的同一份榜单和历史曲线**，而 DSH 插件运行在单个用户的本机，插件注册的 HTTP 路由只服务本机 GUI（`127.0.0.1`），既没有公网入口，也无法承载跨用户的账号、押注与推荐位。

同时，star 历史不可回填：今天不开始抓，就永远缺今天的数据。这一点与「先做哪种形态」无关，必须最先启动。

## 决策

1. **先做网站**：React + TS 前端 + FastAPI 后端 + SQLite，单端口部署在公网服务器，首版只读。
2. **插件后置到 Phase 4**：只有当榜单有稳定流量后，才做轻量 DSH 插件（3 个只读工具 + 一个右侧栏面板），作为分发与召回渠道。
3. **今天开始每日快照**：GitHub Actions 每天 00:10 UTC 抓取 100 个入选仓库，JSON 提交 git，服务器只做 `git pull` + 导入。
4. **API 首版即版本化**：`/api/v1`，为插件与第三方调用预留稳定契约。

## 理由

- **共享状态**：榜单、押注、推荐位都是跨用户状态，插件做不到。
- **数据不可逆**：star 曲线越早累积越好，网站先行不影响数据管线。
- **受众不对称**：插件只覆盖 DSH 用户，而 Claude Code / Codex / Cursor 用户远多于此。
- **变现依赖公网**：推荐位与赞助需要公开页面与流量统计。
- **设计已就绪**：网站的产品设计已完整（7 榜、押注、徽章、推荐位）；插件形态尚未设计。
- **DSH 集成成本低**：右侧栏沙盒浏览器已能直接打开网站，插件不是「能不能被使用」的前提。
- **插件是渠道不是本体**：插件应把用户带回网站，而不是在插件里重建一份数据。

## 后果

- 需要一台公网服务器与域名（域名待定，GitHub OAuth 回调需要）。
- 需要维护每日抓取（Actions 漏跑需手动补跑；服务器侧有 systemd timer 兜底）。
- 插件 Phase 4 的触发条件：周活 ≥ 300 且 DSH 用户占比 ≥ 15%，或 ≥ 20 条插件功能请求，或出现第三方 API 调用。

## 备选方案

- **只做 DSH 插件**：无法承载共享状态与变现，star 历史仍要依赖公网抓取；仅在「个人工具 / 作品集 / 只服务 DSH 用户」时更优。
- **先插件后网站**：把最容易变化的 UI 先绑死在插件 slot 体系上，返工成本高。
- **同时开发**：1C1G 服务器与单人精力都不支持双线并行。
